# M4a demo — Kitchen tickets and printing

```bash
pnpm db:reset      # migrations 0001–0005, demo stations (BBQ, TANDOOR, KARAHI, FRY, DRINKS)
pnpm dev           # api + web; the print worker runs inside the API in development
```

You do not need a real printer: any TCP listener works as one. For example, in a second terminal:

```bash
node -e "require('net').createServer(s=>{let b=[];s.on('data',d=>b.push(d));s.on('close',()=>console.log(Buffer.concat(b).toString('latin1').replace(/[\x00-\x09\x0b-\x1f]+/g,' ')))}).listen(9100,'127.0.0.1')"
```

1. As `owner`, open **Admin → Printers** (or use the API) to register the printer, press *Test page*, and tick the stations it prints. API equivalent:
   `POST /printers {"name":"Kitchen","kind":"KOT","conn_type":"NETWORK","host":"127.0.0.1","port":9100,"paper_mm":80}` → `PUT /stations/<BBQ id>/printers {"printerIds":["<printer id>"]}`
2. In the web app (cashier): open a table, add a tikka and a naan, tick **Rush**, press **Send to kitchen**. The cart lines become *Sent*; a message names the stations; the listener prints one ticket per station.
3. Void a sent line (it asks for a reason) → a **CANCEL** ticket prints. `POST /kots/:id/reprint {"reason":"…"}` → **REPRINT #1**.
4. Stop the listener, send another order → the red *Printer offline* banner appears and `GET /printers/health` shows the queue. Start the listener again → the queue drains in order, once each.

## Endpoints (all under `/api/v1`)

| Area | Endpoints | Needs |
| --- | --- | --- |
| Send | `POST /orders/:id/send {rush?, course?}` → `{order, kots[], unprinted[]}` | `order.create` |
| KOTs | `GET /kots?orderId=`, `GET /kots/:id`, `POST /kots/:id/reprint {reason}` | any · any · `kot.reprint` |
| Printers | `GET /printers/health` · `POST /printers/:id/test` (queues a test page) | any user · `settings.manage` |
| Print queue | `GET /print-jobs?status&printerId&limit`, `POST /print-jobs/:id/retry` | `settings.manage` |

Design: [ADR 0006](../adr/0006-kitchen-tickets-and-print-queue.md). Errors: [ERROR-CODES.md](../ERROR-CODES.md).

## What the tests prove

- **`packages/printing` (26 tests, 100 % coverage):** exact ESC/POS bytes, ASCII-only output (Urdu never reaches the printer), wrapping/columns, KOT/RUSH/REPRINT/CANCEL layouts on 80 and 58 mm paper as readable snapshots.
- **API (`kitchen.test.ts`, 30 tests against real TCP "printers"):** one KOT per station with the right lines on the right printer; 58 mm ticket fits 32 columns; gap-free KOT numbers; courses and rush; atomic `STATION_MISSING`; held/billed/stale-version refusals; **two simultaneous sends → one KOT**; deal components routed to their own stations; cancel tickets (free voids print nothing); reprint rules + audit; **printer unplugged → head job FAILED with 2/4/8/16/30 s backoff, later jobs wait, health OFFLINE; replugged → drained in order, exactly once**; independent printers; **three workers at once → no duplicate, order kept**; idempotent job creation; lease recovery; DEAD after 2 h and admin retry; unsupported/inactive printers don't block; print history can't be deleted.
- **E2E (Playwright):** the web UI sends an order and a real TCP server receives the two KOTs (tikka at BBQ, karahi at KARAHI; the voided chops never printed).
